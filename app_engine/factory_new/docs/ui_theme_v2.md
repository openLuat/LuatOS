# 主题体系 v2 —— 左栏跟随主题 + 主题集重配

> 版本 2.0 · 2026.09.17
> 涉及文件：`ui/ui_theme.lua`、`ui/ui_theme_themes.lua`、`ui/idle_win.lua`
> 关联文档：[`ui_nav_owner_area_plan.md`](./ui_nav_owner_area_plan.md)（左栏常驻是那次导航改造引入的）

---

## 一、要解决的两个问题

1. **主题设置改不动左侧内置应用区域。**
2. **主题之间雷同，且多套是「同一块黑板换了个强调色」。**

两条反馈在源码里都能定位到确切成因，不是观感问题。

---

## 二、根因分析

### 2.1 左栏为什么改不动 —— 三个独立成因叠加

**成因 A：左栏底色借用了 `theme.C.white`，而这个令牌没有任何主题覆写它。**

```lua
-- idle_win.lua（v1）
local rail = theme.box(parent, { x = 0, y = 0, w = rail_w, h = screen_h,
    color = theme.C.white, opa = theme.OPA.rail })          -- ← 借用 white
```

`theme.C.white` 的唯一来源是 `ui_theme.lua` 的基线 `0xFFFFFF`，v1 的 9 套主题
**没有一套**在 `colors` 里覆写它。而 `OPA.rail` 只有三个取值：

| 主题组 | `OPA.rail` | 左栏实际外观 |
|---|---|---|
| 深色玻璃（amber / ocean / violet / forest） | 14 | 几乎透明，与背景融成一片 |
| 浅色实底（dawn / linen / mist） | 220 | 近白面板 |
| 深色实底（obsidian / slate） | 255 | **纯白 0xFFFFFF** |

于是左栏只有**三种**外观。同一档内的主题，左栏像素级完全相同。

**成因 B：深色实底主题的左栏是纯白的。**

`OPA_SOLID_DARK.rail = 255` 配白色的结果 —— 在「曜石纯黑」这套纯黑主题下，
左栏被画成一条 `0xFFFFFF` 的纯白竖栏。实测「曜石纯黑」与「石板石墨」
两套主题的左栏底色 100% 相同（都是 `0xFFFFFF`）。

**成因 C：换肤只打脏标记，等 `on_get_focus` 才重建。**

```lua
-- idle_win.lua（v1）
local mark_theme_dirty, take_theme_dirty = theme.dirty_flag()
sys.subscribe("UI_THEME_CHANGED", mark_theme_dirty)   -- ← 只设一个局部标志
```

而 `take_theme_dirty()` 只在 `on_get_focus` 里被消费。

这套机制在改造前是成立的：页面铺满整屏，桌面被完全遮住，用户看不到它有没有变色。
**但导航改造之后左栏是常驻可见的** —— 上层页面只占右侧内容区。
用户在设置里点主题时，左栏就在旁边，而它要等用户回到桌面才会重建。
**当下看到的就是「主题改不动左栏」。**

> 这三条叠在一起，解释了为什么这个 bug 只在宽屏出现：窄屏 `use_rail = false`，本就没有左栏。

### 2.2 主题为什么雷同 —— 底的明度过于集中

对 v1 的 9 套主题做了 CIE76 ΔE 审计（Lab 空间，取 bg / panel / t1 / accent / stroke 五项均值）：

| 观察 | 数据 |
|---|---|
| 最接近的一对 | `forest ↔ obsidian` 均 ΔE **8.7**（bg ΔE 仅 7.4） |
| 次接近 | `ocean ↔ slate` 11.1（bg ΔE **5.0**）、`dawn ↔ linen` 12.2 |
| 浅色 3 套的底色 | `0xEEF2F7 / 0xF5F0E8 / 0xE9EBEF` —— 全挤在 `0xE9~0xF5`，`dawn ↔ mist` 的 bg ΔE 仅 **2.5** |
| 深色 5 套的底色 | `0x0D131C / 0x0A1620 / 0x110C1C / 0x0A1512 / 0x000000` —— 全挤在 `0x00~0x11` |
| **中间明度** | **完全空白** |

结论：9 套主题实际只有「深 / 浅」两个明度档，档内靠色相区分，而色相在暗色区
（亮度 10 上下）的辨识度很低 —— 用户在设置页看到的就是「同一块黑板换了强调色」。

顺带查出的对比度问题：浅色 3 套的 `t3`（弱文字档，也用在左栏应用名上）
对底色只有 **2.6 / 2.8 / 2.6**，低于 3:1 下限。

## 三、主题集 v2 设计

### 3.1 设计原则：按「明度档 × 色相」两维铺开

v1 的问题不是「套数太多」，而是「维度太少」。v2 收敛为 **8 套**，
在**明度**上铺三段，每段内用**色相**区分：

| # | id | 名称 | 档位 | 外观 | 底色 | 强调色 |
|---|---|---|---|---|---|---|
| 1 | `dawn` | 晨曦浅色 | 浅色 | 实底 | `0xEAF0F8` 冷蓝白 | 琥珀 `0xB86E08` |
| 2 | `linen` | 暖阳米色 | 浅色 | 实底 | `0xF8F0E2` 暖米黄 | 赭橙 `0x9C4F17` |
| 3 | `jade` | 青瓷清露 | 浅色 | 实底 | `0xE4F2E8` 青绿 | 松绿 `0x1F7A55` |
| 4 | `dusk` | 暮色蓝灰 | **中间** | 实底 | `0x36404D` 蓝灰 | 天青 `0x7FCCF0` |
| 5 | `clay` | 陶土暖棕 | **中间** | 实底 | `0x4A3E36` 棕灰 | 陶橙 `0xF0A46A` |
| 6 | `amber` | 琥珀夜空 | 深色 | 玻璃 | `0x0D131C` 蓝黑 | 琥珀 `0xFFB454` |
| 7 | `forest` | 青竹幽谷 | 深色 | 玻璃 | `0x0E2619` 墨绿 | 竹青 `0x4FD69C` |
| 8 | `obsidian` | 曜石纯黑 | 深色 | 实底 | `0x000000` 纯黑 | 薄荷 `0x5EE6A8` |

**相对 v1 的增删：**

| 操作 | 主题 | 理由 |
|---|---|---|
| 删除 | `mist` | 与 `dawn` 的 bg ΔE 仅 2.5，肉眼不可分 |
| 删除 | `ocean` | 与 `amber` 的 bg ΔE 仅 2.4 |
| 删除 | `violet` | 与 `amber` 的 bg ΔE 5.8，同属「深蓝黑玻璃」 |
| 删除 | `slate` | 与 `obsidian` 同为深色实底，与 `ocean` 的 bg ΔE 5.0 |
| 保留 | `dawn` `linen` `amber` `forest` `obsidian` | —— |
| **修正** | `forest` | 底色 `0x0A1512` → `0x0E2619`。原值暗到与纯黑难分（ΔE 7.4，全表最接近的一对） |
| **新增** | `jade` `dusk` `clay` | 补浅色自然档 + **填补完全空白的中间明度档** |

> **关于「删除」的影响**：主题 id 同时是持久化到 fskv 的值。用过被删主题的设备，
> 下次启动时 `theme.restore()` 读到的 id 在 `M.THEMES` 里找不到，
> 会回落到 `M.DEFAULT_THEME`（dawn）。这是可接受的降级，不需要迁移代码。

### 3.2 三段明度的取舍

中间档（`dusk` / `clay`）是 v2 最大的新增，需要单独说明它的技术约束：

- **必须走实底**（`wallpaper = false`）。玻璃语言的半透明白在中明度底上不会
  形成层次，只会糊成一片脏灰。
- **`surface` 要改成卡片实色**（如 `0x424E5C`）而不是白色。`OPA_SOLID_DARK`
  把 `glass` 提到 255，卡片就是 `surface` 实心块 —— 它必须比 `bg` 亮一档才分得出层次。
- **文字转浅色**。底色 `0x36404D` 相对亮度 0.049，深色文字完全不可读。
- 这两个约束在 `ui_theme_themes.lua` 的 `OPA_SOLID_DARK` 注释里写明了。

## 四、左栏 token 化

### 4.1 新增两个令牌

```lua
-- ui_theme.lua · M.C
rail_bg     = 0xFFFFFF,   -- 左栏底色（主题各自覆写）

-- ui_theme.lua · M.OPA
rail_active = 48,         -- 左栏选中底块透明度（浅色主题覆写为 96）
```

### 4.2 左栏底色：每套主题各自给出

| 档位 | 策略 | 取值 |
|---|---|---|
| 浅色档 | 近白（左栏在浅底上本就该是白面板），靠微色偏区分 | `0xFFFFFF` / `0xFCF7EF` / `0xF4FAF6` |
| 中间档 · 深色实底 | 与 `bg` 同族、略暗一档的深色，与内容区拉开层次 | `0x2E3742` / `0x3E342D` / `0x0C0F13` |
| 深色玻璃 | **带本主题色相的半透明白** + 透明度，让桌面光斑与主题色一起透上来 | `0xFFD9A0`（暖琥珀）/ `0xBFF2DA`（竹青）（opacity 由 `OPA.rail` 控制） |

同时把玻璃档的 `OPA.rail` 从基线的 **14 提到 40**（约 16%）—— 14 淡到几乎与背景
融成一片，而 26 也不够：两套玻璃主题（琥珀夜空 / 青竹幽谷）的左栏合成色只差 ΔE 5.6，
用户在主题页来回切这两套时看到的就是「左栏没变」（v2.1 修的就是这条，见第九节）。
40 仍然透明到能透出光斑，且各主题 `rail_bg` 的色相能真正显出来。

### 4.3 左栏标签文字：`t3` → `t2`

左栏底色是「`rail_bg` 叠在主题 `bg` 上」的合成色，比纯 `bg` 亮一档。
在 `amber` 主题下合成色是 `0x262B33`，`t3`（`0x5E6978`）在其上只有 **2.6:1**，
低于 3:1 下限。`t2` 在全部 8 套主题的左栏上都 ≥ 5.2:1。

语义上也更对：左栏标签是主导航文案，对应「次级文字」而非「弱文字」。

### 4.4 换肤时立即重建左栏

```lua
-- idle_win.lua
local function on_theme_changed()
    mark_theme_dirty()          -- 保留：回到桌面时整屏重建
    if not rail_rebuild_timer then
        rail_rebuild_timer = sys.timerStart(rebuild_rail_now, 40)
    end
end
sys.subscribe("UI_THEME_CHANGED", on_theme_changed)
```

三个设计点：

1. **只重建 rail，不整屏重建。** 桌面右区此刻被上层页面完全遮住，重建它纯属浪费；
   而且整屏重建会走 `on_lose_focus` → 顺带销毁并重起视频解码。
2. **延迟 40ms。** 换肤是在主题卡片的点击回调里发起的，在回调栈上销毁容器不安全。
   40ms 远小于人眼可辨延迟，观感上就是「立刻」。
3. **保留脏标记。** 回到桌面时 `on_get_focus` 仍会整屏重建（把右区也换成新配色），
   这条路径没变。

**⚠️ 一个必须守住的约束：** `local rail_rebuild_timer` 的声明位置**必须早于 `on_destroy`**。

Lua 的词法作用域按声明位置计算 —— 如果声明写在 `on_destroy` 定义之后，
`on_destroy` 里的同名引用会落到作用域之外、解析成**全局变量**，
「销毁时停掉待触发的重建定时器」这条清理会静默失效（读写的不是同一个变量）。
断言脚本里有一条专门卡这个顺序。

## 六、给后来者的规范

### 6.1 新增一套主题

复制 `ui_theme_themes.lua` 里任意一个 preset，改 `id / name / desc / colors / swatch`，
追加一次 `theme.register(preset)`。设置页会自动列出，不需要改任何页面代码。

**必须守住两条硬约束**（否则又退化成「雷同」）：

1. **与同档位其他主题的底色有可辨差异** —— 浅色档内 bg ΔE ≥ 8，深色档内 ≥ 10。
2. **对比度达标** —— `t1/bg` ≥ 4.5、`amber/bg` ≥ 3.0、`t3/bg` ≥ 3.0。

跑一遍审计脚本即可验证（见 `theme_audit_v2.py`）。

### 6.2 三条容易踩的坑

| 坑 | 说明 |
|---|---|
| `rail_bg` 必须显式给出 | 不写就回落到基线的 `0xFFFFFF`。深色主题忘记写 = 一条纯白左栏（v1 的 bug 就是这么来的） |
| 中间明度主题别开玻璃 | `wallpaper = true` 在中明度底上只会糊成一片；且 `surface` 要改成卡片实色 |
| `desc` 里的分隔符只用 `|` | 固件内置字库（hzfont）不含中点 `U+00B7`，渲染成方框 |

### 6.3 令牌速查

| 令牌 | 用途 | 谁在用 |
|---|---|---|
| `C.rail_bg` | 左栏底色 | `idle_win.build_rail` |
| `OPA.rail` | 左栏底色透明度 | 同上 |
| `OPA.rail_active` | 左栏选中底块透明度 | `idle_win.build_rail`（选中块颜色取 `C.amber`） |
| `C.amber` / `C.primary` | 主强调色（历史原因写在 amber 槽位） | 全工程 |

## 八、待确认

1. **左栏在浅色档内的差异偏小**（底色 ΔE 4.2~12.3）。浅色主题的左栏本就该是白面板，
   真正拉开辨识度的是品牌块与选中块的强调色。若希望左栏本身差异更明显，
   可以把浅色档的左栏改成跟随 `panel_hi`（会牺牲一点「白左栏」的干净感）。

   但两者底色 ΔE 19.4、且一个玻璃一个实底，实测区分度足够。若需要更大差异，
   把 `forest` 的强调色改为偏黄绿的竹叶色即可。
3. **未做的历史遗留**：`theme.rail()`（`ui_theme.lua`）是从未被调用的死代码，
   与 `idle_win.build_rail` 重复实现，可清理。

## 九、v2.1 修订：两套玻璃主题的左栏

> 用户反馈：「琥珀夜空主题和青竹幽谷主题左侧内置应用区域没改变」。

### 9.1 为什么 v2.0 漏掉了这条

v2.0 给每套主题都显式写了 `rail_bg`，但**两套玻璃主题给的是同一个值**
（`0xFFFFFF` + `OPA.rail = 26`）—— 等于只解决了「深色实底档变成纯白左栏」那半边问题：

| 主题 | 底色 | `rail_bg` | 合成色 | 栏上 `t2` |
|---|---|---|---|---|
| amber | `0x0D131C` | `0xFFFFFF` | `0x2D2E31` | `0x95A0AE` |
| forest | `0x0E2619` | `0xFFFFFF` | `0x273C30` | `0x94B3A4` |

合成色 ΔE 只有 5.6，`t2` 也几乎一致 —— 左栏只有 100px 宽、对比又低，
**实际观感就是「没变」**。上一轮审计只卡了「ΔE < 3（肉眼不可分）」，
5.6 从这道门缝里过去了。

### 9.2 修法

| 改动 | 前 | 后 |
|---|---|---|
| `OPA_GLASS.rail` | 26 | **40**（≈16%） |
| amber `rail_bg` | `0xFFFFFF` | **`0xFFD9A0`**（暖琥珀） |
| forest `rail_bg` | `0xFFFFFF` | **`0xBFF2DA`**（竹青） |
| amber / forest 左栏 ΔE | 5.6 | **16.8** |

设计口径：**玻璃档的「是哪一套主题」由各主题自己的 `rail_bg` 色相承担**，
`OPA.rail` 只负责「有多透」。这比继续加白更对 —— 加白永远只是「更亮一点的白」，
加色才能在 100px 宽的低对比面板上被认出来。

### 9.3 判据升级

审计脚本新增 **「同档位内左栏 ΔE ≥ 8」**：

- 只在同档位内要求 —— 跨档位时整屏明度差异足够大，左栏差 ΔE 6 不影响判断；
- **浅色档豁免**（那三套的设计就是近白微色偏，见文件头）。

原「ΔE < 3」判据保留但不再作为唯一门限（它正是漏掉本条的原因）。

> 交叉引用：本轮四条缺陷的完整记录见 [`ui_defect_fixes.md`](./ui_defect_fixes.md)。

## 十、v3 修订：主题集回到 9 套、新增科技蓝 / 活力橙、去掉壁纸光斑

> 用户反馈：「增加一个科技蓝主题和活力橙主题」「整体保持 9 个主题，去除不美观的主题，背景的四个球不要了」。

### 10.1 主题集 8 → 9：淘汰 `dusk`，补入 `techblue` / `vivid`

8 + 2 = 10，按「保持 9 套」的约束必须去掉 1 套。被淘汰的是 **`dusk` 暮色蓝灰**：

| 候选 | 判断 |
|---|---|
| `dusk` 暮色蓝灰（`0x36404D`） | **淘汰**。去饱和的灰蓝板，本身记不住；而新加的「科技蓝」与它同档位、同色相，两套并排就是「同一块蓝板调了下灰度」 |
| `clay` 陶土暖棕（`0x4A3E36`） | **保留**。「活力橙」被刻意往亮里拉开（`0x8A4A18`，饱和度拉满），两者底色 ΔE 达 **39.9**，可以共存 |

剩下的中间档就此形成「一冷一暖一陶土」：`techblue`（宝蓝）/ `vivid`（饱和橙）/ `clay`（灰陶）。

**两套新主题的设计要点：**

| | 科技蓝 `techblue` | 活力橙 `vivid` |
|---|---|---|
| 底色 | `0x1E3E74`（宝蓝） | `0x8A4A18`（饱和橙） |
| 强调色 | `0x4FA3FF`（电光蓝） | `0xFFB454`（活力橙） |
| 左栏 `rail_bg` | `0x14284D`（深蓝，OPA 255） | `0x5E2F0C`（深橙，OPA 255） |
| 外观 | 实底 | 实底 |
| 正文 / 强调 / 弱文字对比度 | 9.25 / 4.01 / 4.24 | 6.25 / 3.87 / 3.39 |

两套都走**实底**而不是玻璃 —— 中明度底上叠半透明白卡只会糊成一片脏灰（v2 已确立的规则）。
「暖色 + 中明度」最容易糊，所以 `vivid` 把卡片 / 输入框 / 轨道全部往更深的橙里走
（`0x5E2F0C`），靠「亮底 + 深控件」拉开层次，而不是靠白色半透明层。

### 10.2 去掉壁纸的四个光斑球

`M.wallpaper` 里原本有四处 `M.blob(...)` —— 用「超大圆角的方块」近似径向渐变光晕，
分别落在左上 / 右上 / 右下 / 左下：

```lua
M.blob(base, -w*0.18,        -h*0.34,        w*0.56, M.C.violet,    52)
M.blob(base,  w - w*0.34,    -h*0.38,        w*0.60, M.C.cyan,      44)
M.blob(base,  w*0.52,         h - h*0.52,    w*0.72, M.C.blob_pink, 28)
M.blob(base, -w*0.06,         h - h*0.44,    w*0.52, M.C.cyan,      24)
```

这是 AirUI 没有径向渐变能力时的近似手段，但实机上**更像四块贴上去的色斑**，
而不是「光晕」。本轮按反馈全清：

| 删除项 | 位置 |
|---|---|
| 4 处 `M.blob(...)` 调用 | `ui_theme.lua` 的 `M.wallpaper` |
| `M.blob` 函数本身 | `ui_theme.lua`（已无调用方，不留死代码） |
| `blob_pink` 令牌 | `ui_theme.lua` 基线表 1 处 + 9 套主题各自的覆写（共 10 处） |

壁纸现在只剩「底色 + 顶部渐隐」这条真渐变（`M.bg_top` 用 10 段窄条的透明度递减近似），
更干净，也没有了「四角各一个圆」的廉价感。

> 只有 `wallpaper = true` 的两套玻璃主题（`amber` / `forest`）会走到这段代码，
> 其余实底主题本来就只有一层纯色底。左栏的合成色因此只由「`rail_bg` 色相 + `OPA.rail`」决定，
> 不再受光斑影响 —— 这反而让 9.2 那套「靠色相区分左栏」的口径更纯粹。
