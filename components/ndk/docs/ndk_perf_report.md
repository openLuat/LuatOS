## 5. 分析与结论

### 5.1 Base64 编码是 NDK 的杀手场景

三台设备上 Base64 编码在所有数据规模下 NDK 均大幅领先，加速比 **1.9x ~ 7.1x**。原因：
- Base64 编码含密集分支（6-bit 分组 → 字符映射表查找）和 4/3 展开比
- 编译后的 RISC-V 代码在分支预测和循环展开上远优于 Lua 解释器
- 数据量越大，NDK 的固定开销（exec/setData/getData）摊薄越明显

### 5.2 Air780EHM 的 NDK 优势最显著

780EHM 上 NDK 在 10/13 项中胜出，而 1602 和 8101 上仅 4-5 项。原因：
- 780EHM 使用 **32bit Lua VM**，Lua 解释器本身较慢
- 1602 和 8101 使用 **64bit Lua VM**，Lua 执行效率更高
- 780EHM 的 CPU（Cortex-R）对 RV32IMA 解释器的整型运算有较好的流水线支持

### 5.3 简单算法 + 小数据 = NDK 劣势

FNV-1a、CRC32 等简单算法在 64B 数据上，三台设备均为 Lua 胜出（0.54x ~ 0.86x）。原因：
- 算法本身计算量极小（FNV-1a 仅一次乘法 + 一次异或/字节）
- NDK 的 `setData → exec → getData` 固定开销（约 0.1-0.3ms）占比过大
- Lua 直接在内存中操作，无上下文切换成本

### 5.4 MD5 的平台差异性

- 780EHM：NDK 赢（1.39x ~ 1.77x），32bit Lua VM 拖慢了 Lua 侧
- 1602：Lua 赢（0.52x ~ 0.63x），64bit Lua VM 的数学运算足够快
- 8101：Lua 赢（0.52x ~ 0.80x），同 64bit Lua VM

### 5.5 NDK 适用场景建议

| 场景 | 推荐 | 原因 |
|------|------|------|
| Base64/编码类大数据块 | ✅ NDK | 2-7x 加速，数据越大优势越大 |
| MD5/哈希（32bit 平台） | ✅ NDK | 1.4-1.8x 加速 |
| MD5/哈希（64bit 平台） | ❌ Lua | Lua VM 本身足够快 |
| 简单算法小数据（FNV/CRC） | ❌ Lua | NDK 固定开销占比过大 |
| 排序（32bit 平台） | ✅ NDK | 1.1-1.3x 加速 |
| 排序（64bit 平台） | ❌ Lua | Lua VM 更快 |
| 不可信/第三方算法 | ✅ NDK | 沙箱隔离，安全优先于性能 |
