# Air8000 Zenoh Pico专用固件配置与后续验收请求

这是构建需求和整改步骤，不是已分配编号、已构出的SoC或容量通过报告。C首错诊断与目标Get根因修复、新配置容量和长期稳定性分别验收。

## 已知问题及C整改

专用测试设备在V2055/113/64位上已通过短包双向Get、显式撤销、关闭重开和4096B Pub/Sub原值回显。随后4096B Query请求出现`-7`，对端未观察到该Query；不能仅据错误码认定为尺寸限制、内存不足或网络故障。

后续TEMP2222专板已通过Wi-Fi入网和基础TCP；原生OPEN在首条TCP日志之前停滞，CLOSE保持CLOSING。该包ELF表明事件接收的空队列路径把超时0变成永久等待，而TCP在open/read/send/close前均调用它。本PR统一改为有限1ms，并同步主机事件桥，使旧参数明确失败、不再以空队列立即返回掩盖缺陷。

另修正close与工作任务状态发布的竞争：使用同一短门保护generation接纳和ONLINE/FAILED发布；close已接纳后不能被迟到的打开结果覆盖，已打开的SDK资源仍正常清场。保留既有首错阶段/原码/接纳字节诊断，回归真实SDK成功/失败结果交错、下一代重开及资源回收。

这些是有源码和目标反汇编依据的修正，尚未进入新目标SoC。不能据此宣布历史4096B Get的`-7`已解决；它是上层会话失败汇总代码，必须在新包复验原场景。

目标定位次序：大PUT后短Query；独立4096B请求配短回复；空请求配4096B回复；反向Query的两份4096B回复；2047/2048/2049/4095/4096边界。取得首次失败层后做单一原因的最小C修复，回归原始“4096B PUT回显→4096B Query→两份4096B回复/Final”组合，不以小请求替代大请求修复。

## 新配置要求

现有生产代码的脚本镜像已经超过512KiB。若仍只提供512KiB脚本空间，需要反复拆包、删除和替换组件，显著增加实际业务联调与回归成本。因此本次申请的测试固件必须提供至少1024KiB脚本分区，便于用接近实际业务规模的脚本验证；512KiB包不能满足本次集成测试需求。

- 以112功能基线形成独立新编号，由维护者分配数字，不覆盖113或仅重命名文件。
- Lua64；**脚本Flash分区至少1024KiB＝1,048,576字节**，指脚本镜像分区容量，格式开销另计，不是Lua堆或SoC文件大小。
- 裁掉字库、LCD/触摸、U8G2/U8X8、EINK/EPD、HT1621及显示独占的字体/绘图/屏驱动/图片资源。
- JPEG解码、二维码生成等附属只有经反向引用确认不被其他功能使用时才裁；公共注册对象和通用总线/内存实现不能整件删除。
- 加入完整Pico的Pub/Sub、Get、Queryable、reply/final/poll，以及本PR有限事件等待、关闭竞争修正和既有首错诊断；不能通过关闭Get制造容量通过。

112基线脚本区已有1024KiB；当前113 TEMP2222包为512KiB且仍声明显示组件。因此优先从112组合做显示裁剪，不默认从113扩脚本。若选113备用方案，需额外净增512KiB脚本分区并重算AP/FS/FOTA边界。最终都以实际BSP产物为准。[官方编号与容量表](https://docs.openluat.com/air8000/luatos/firmware/)

## 需要的构建输出

同源码/BSP/SDK/工具链/优化和Lua位宽，构建112参考、裁显示Pico关闭、同裁剪完整Pico开启三组；按需补同Pico开启但未裁显示的对照。提供：

1. LuatOS/BSP/SDK commit、工具链版本、有效宏/头文件顺序/源表；默认SDK1.9.0，差异显式列出。
2. 每组真实编译/链接/打包退出、ELF/map/size、计入AP上限的有效用量/上限/余量和精确超限字节；维护余量在构建前固定。
3. AP/CP、脚本与升级暂存、FOTA、FS、FDB、NVRAM、备份/异常区的完整分区及对齐/重叠验证。
4. 静态RAM、堆栈配置、诊断event增量，后续补实际堆峰值/栈水位；Flash扩容不等于运行RAM扩容。
5. SoC SHA、官方编号、包metadata与生效配置一致性、跨编号迁移及同编号升级/回退规则、持久数据影响说明。

最终AP余量＝新AP上限−最终计限用量；Pico增量用同裁剪配置on/off差值，裁剪收益用同Pico配置裁前/裁后差值。历史对象归属、源码长度、填充容器及SoC压缩文件长度不能替代这些数据。

1024KiB验收应包括超过旧512KiB、接近新有效上限、超限拒绝的合法脚本镜像离线构包，以及专板加载/校验/后续更新。不能仅把metadata改大；分区生成源、链接上限、包地址和升级暂存须同步。

## 构建协作和真机阶段门

本次集中请求：基于本PR最终提交统一重编组件、目标适配和注册，按112基础裁剪显示，提供Lua64、至少1024KiB脚本区的独立新编号测试SoC；不要混用旧对象或仅改包名/metadata。当前公开仓库不含完整Air8000型号构建输入，故这里提交精确构建要求，不伪造目标分区配置。若同源构建未达容量，请回传计限用量与超限字节，再据实选择裁剪，不以压缩包长度推断。

TEMP2222 map中显示链116个唯一对象合计189742字节（约185.29KiB），只是未压缩对象归属，不等于可回收的压缩AP空间，更不足以证明从113净增512KiB可行；不能与历史112对象估算叠加。优先验证112已有1MiB脚本布局。完整布局和AP余量仍须上述同源构建签收。

通用RTOS事件API目前仅约定0成功、非0失败，没有可移植的“空队列/超时/真实错误”枚举，本PR不硬编码某BSP的-6/-13。统一network连接/关闭仍依赖BSP定时器事件；timer启动失败路径尚未在目标验证。本次不改共享network状态机，主机通过不能替代此项保障。

新包先离线检查ABI、编号、分区、容量和恢复材料，再在专用测试设备执行：模块→WiFi扫描/联网→TCP→短包双向Get→原4096B失败组合→边界/生命周期→30分钟、2/8/24小时独立长稳。长稳负载、计数、内存/队列/时延判据和未知处置在执行前固定，不能拼接多个短窗冒充连续通过。

容量/生命周期、认证及完整Lua业务替代按后继PR继续，64KiB逻辑payload需要独立有界内存设计。新号、PR合入或主机通过均不代表目标Get故障关闭或生产验收完成。
