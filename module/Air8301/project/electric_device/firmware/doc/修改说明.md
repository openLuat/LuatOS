#### 2. 变更原因
运行时报错：`aircloud_app.lua:138: attempt to concatenate a boolean value (field 'error_msg')`。
根因：`excloud` 的 `send_result` 事件中 `error_msg = success and "Send successful" or err_msg`，
而 `socket.tx` 失败时 `err_msg` 可能为布尔值 `true`，直接做字符串拼接导致崩溃，
并使本次回调中断（后续喂狗 / 断线重连逻辑未执行）。

#### 3. 变更内容
- `code/aircloud_app.lua`：新增本地 `safe_str()` 安全转字符串函数；
- 对事件回调中可能为非字符串的字段统一做类型保护：
  - `connect_result.error`、`auth_result.message`、`message.header.sequence_num`、
    `reconnect_failed.count`、`send_result.error_msg`；
- `send_result` 失败分支：`string.find` 前加 `type(err) == "string"` 判断，
  仅当错误信息为字符串且明确指示 TCP 不可用时才强制重连。

#### 4. 影响范围

#### 1. 变更类型

#### 2. 变更原因
**故障现象**：RS485（UART1，对接高压控制板）**能收到数据、但发不出数据**。

**根因**：Air8301 的 RS485_1 为**半双工**通道，收发方向由 RE/DE 脚 **GPIO2** 控制
（高电平=发送，低电平=接收），必须通过 `uart.setup` 第 8/9/10 参数
（`rs485_gpio` / `rs485_level` / `rs485_delay`）交给固件自动换向。
而移植时 `uart_app.lua` 按"TTL 全双工"初始化，**只传了前 5 个参数**：

```lua
uart.setup(UART_ID, UART_BAUD, DATA_BITS, STOP_BITS, PARITY)   -- 缺 485 方向控制参数
```

导致 GPIO2 从未被驱动 → 485 收发芯片**始终停留在接收态** → MCU 的 TX 数据发不到 A/B 总线；
且 Air8000W（Air8301 主控）在缺少 `pin485` 参数时 `uart.write` 会直接返回 **-1**。

**判定依据**：
- `hardware_test/app/rs485_app.lua`（Air8301 已验证驱动）：
  `uart.setup(1, 115200, 8, 1, uart.NONE, uart.LSB, 1024, 2, 0, 20000)`；
- `hardware_test/app/board_init.lua` 注释："RS485 RE/DE 由 uart.setup 内置 RS485 模式控制，本模块不操作 GPIO2/153"；
- 合宙官方 FAQ：方向脚须传 `uart.setup` 第 8 参数，第 10 参数 `rs485_delay` 按波特率设置（**9600bps 填 20000us**）；
- RX 正常（波特率/接线/GPIO29 供电均正确），故障点锁定在方向控制。

#### 3. 变更内容
- **`code/uart_app.lua`**：
  - 新增 RS485 方向控制常量：`RS485_RE_DE_PIN = 2`、`RS485_RX_LEVEL = 0`、
    `RS485_TX_DELAY = 20000`（9600bps）、`UART_RX_BUFF_SIZE = 1024`；
  - UART1 初始化改为启用**固件内置 RS485 自动换向**（第 8/9/10 参数）：
    ```lua
    uart.setup(UART_ID, UART_BAUD, DATA_BITS, STOP_BITS, PARITY,
        uart.LSB, UART_RX_BUFF_SIZE, RS485_RE_DE_PIN, RS485_RX_LEVEL, RS485_TX_DELAY)
    ```
  - 初始化日志追加 RS485 模式与方向脚信息；
  - `send_ctrl_frame()` 增加 `uart.write` 返回值校验：返回 `<= 0` 时打印告警日志
    （便于定位"发送失败"，不写运维日志以免 1 秒 1 条过频）；
  - 修正文件头"按 TTL 全双工方式初始化"的**错误注释**，改为半双工 RS485 说明。
- `code/board_init.lua` **未改动**：GPIO2 由 `uart.setup` 接管（与 hardware_test 一致，避免手动操作冲突）。

#### 2. 变更原因
**故障现象**：后台下发「开关机指令」（Type=19，265=0/1）与「设定电压指令」（800=5000）后，
**待机界面的开关机按钮、工作状态、设定电压显示值均无变化**，疑似也未通过 UART 下发新数据。

**根因分析（由日志确定）**：平台下发的 Type=19（ASCII 字符串）**Value 域是「裸数组 JSON 字符串」**，
不是协议文档 8.4.1 描述的二进制嵌套 TLV：

```
30 13 00 2F 5B7B226669656C645F6D65616E696E67223A3236352C22646174615F74797065223A302C2276616C7565223A317D5D
   └Type┘└Len┘ └──────────── ASCII："[{"field_meaning":265,"data_type":0,"value":1}]" ────────────┘
```

若协议层只识别 `sub.field`（键名不符）且不对字符串做 `json.decode`，则 `ctrl_fields` **恒为空**：

```
解析失败 → ctrl_fields 为空 → next(ctrl_fields) 为假 → 不发布 "CTRL_CMD_RECV"
        → business_app 不执行命令 → ①UI 不刷新 ②不发布 UART_SEND_CTRL（uart 缓存不变）
        → 三个现象同源（一条根因解释全部症状）
```

**排查困难的放大器**：原实现在解析失败时**完全静默**（无任何日志），
单看日志只能看到 `TLV字段 含义: 19 ...`，无法判断是"没收到命令"还是"收到但没解析出来"。

> 注：日志中**未出现** `protocol_app 收到控制命令` 一行，说明产生该日志的脚本**不含 JSON 解析分支**
> （即未烧录本次修复版本），或 `json.decode` 当场失败；本次加固对两种情况均已覆盖。
