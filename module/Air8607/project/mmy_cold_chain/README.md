# 冷链温控中枢（mmy_cold_chain）

挂在冷库值班室墙面或车间走廊的一块常亮温控看板。用 Air8607 + 10 寸 1024x600 RGB 屏，
把 **8 个冷库温区、压缩机负载、今日能耗、事件流** 摊在一屏里，
让值班的人**不用走近、不用点开、扫一眼**就知道：有没有哪扇门敞着、哪个库开始飘温。

- 平台：Air8607 / 10 寸 RGB 1024x600 / GT911 电容触摸 / 板载 DAC + HT6873 功放
- 框架：airui（LVGL 9），界面全部矢量图元绘制，**不使用任何图片资源**
- 数据：内置冷链仿真引擎（可换真实 Modbus 温湿度模块 / 冷库控制器，见文末）

**版式按"提问顺序"排**：先给结论（KPI 四块），再给过程（曲线 + 温区矩阵），
最后给出账（事件流 + 今日汇总）。值班的人第一个动作是"扫 KPI"，第二个动作才是"找哪个库"，
所以温区矩阵放在视觉中心，八个格子等权，谁飘温谁自己变色。

## 交互

| 区域 | 操作 | 效果 |
|------|------|------|
| 温区砖块 | 点一下（非当前选中） | 选中该温区：曲线切到它的 24h，右侧"当前/设定/容差"同步 |
| 温区砖块 | 再点同一块 | 开 / 关该库库门（演示与现场测试通用），事件流记一条 |
| 曲线卡「除霜」 | 点胶囊 | 对选中温区触发一次除霜（约 13 分钟仿真），期间温度会短时上浮 |
| 事件行 | 点任意一条 | 确认该条：严重度竖条变灰、文字加"已确认"前缀 |
| 事件卡头「全部确认」 | 点一次 | 一次清掉所有待确认事件 |
| 右下角语音键 | 点一下 | 开 / 关语音播报（关掉时功放也拉低，夜班没有底噪） |
| 全屏 | 12 秒无人操作 | 温区自动轮播（展厅 / 走廊看板模式） |

所有反馈都走**事件流 + 语音**，不弹窗：这块屏是常亮信息板，浮层遮住数据反而碍事。

## 视觉约定（`code/theme.lua`）

现场光线杂（穿棉衣的、隔玻璃看的都有），所以对比度优先、颜色少而准：

| 色 | 含义 | 用在哪 |
|----|------|--------|
| 冰蓝 `cold` | 冷 / 正常 | 主强调色、正常温区读数 |
| 霜青 `frost` | 除霜中 | 除霜胶囊、选中框的角标 |
| 暖橙 `warm` | 门开 / 接近阈值 | 门开方块、预警读数 |
| 报警红 `alarm` | 超温 / 断链风险 | 超温温区、报警事件、顶部状态点 |
| 节能绿 `ok` | 正常 / 省电 | 状态点、容差带、语音键 |

**"正常"必须是安静的蓝，"异常"才允许出现红。** 一块常亮屏如果到处是红点，
值班的人两天就会开始无视它。所以正常态的温区砖块底色只压一层极暗的面板色，
只有越界时才整块染色 + 加描边。

字体注意：`hzfont` 是矢量字库，没有中间点（·）、度数（°）、箭头（→）这类符号，
本工程界面文本只用 ASCII + 汉字 + 斜杠 + 负号，温度写成 `-18.4C`，用了 ° 会显示方框。

## 仿真模型（`code/cold_data.lua`）

每个温区是一个一阶惯性环节：

| 量 | 模型 |
|----|------|
| 制冷拉回 | 温度按 `(设定值 - 当前) × 0.95` 的速率回拉 |
| 开门扰动 | `(环境温度 - 库温) × 0.55` 的速率抬升 —— 温差越大进热越快，所以速冻库开门最伤 |
| 除霜 | 蒸发器停冷 0.22 仿真小时，额外 +1.4/小时往上顶 |
| 环境温度 | 正弦：凌晨 22C、午后 30C（这就是现场"下午最容易超温"的原因） |
| 状态分级 | 偏离 ≤ 容差 = 正常；≤ 2 倍容差 = 预警；超出 = 超温（有边沿才记事件，不刷屏） |
| 压缩机负载 | 各温区制冷需求按功率权重加权（冷冻 1.2~1.6、冷藏 0.6~0.85） |
| 能耗 | `负载 × 42kWh/h × 推进小时`，电价 0.78 元/度、碳排 0.581kg/kWh |
| 24h 历史 | 96 点（15 分钟一格），按"装卸货时段 8/14/20 点"的高斯包络生成尖峰，固定种子可复现 |

演示倍率 `theme.perf.demo_speed = 40`：1 秒 = 40 秒仿真，**36 分钟走完一天**，
所以在展厅站着看十几分钟就能看到一次完整的"开门 → 飘温 → 恢复"过程。
接真实数据时把 `settle()` 里的物理部分删掉、改成写 `z.temp` / `z.door` 即可，
UI 只读字段，一行不用改。

## 语音播报（`code/voice.lua`）

面板主体是"看"的，语音只补两件事：**用户刚做的动作有没有生效**、**温度拐点了**。
两个入口语义不同：

| 入口 | 用在哪 | 冲突策略 |
|------|--------|----------|
| `voice.say(text)` | 选温区、开关门、除霜、确认报警 | 立即播；正在播就把这句挂起（只留最后一句，不积压） |
| `voice.auto(text)` | 超温 / 恢复 / 开门超时（由 `ui_main` 监听事件流触发） | 忙就丢弃、10 秒冷却、同句 30 秒去抖 |

后端按固件能力自动降级，PC 模拟器落到静音模式（界面照常，右下角标"PC 模拟器无语音"）：

| 优先级 | 后端 | 条件 | 起播方式 |
|--------|------|------|----------|
| 1 | `ex_tts` | `exaudio` + (`audio_v2.tts` 或 `audio.tts`) | `exaudio.play_start{type=1, content=文本}` |
| 2 | `av2_tts` | 只有 `audio_v2.tts` | 自己配 DAC + PA，`audio_v2.tts()` |
| 3 | `aud_tts` | 只有旧框架 `audio.tts` | `audio.config` + `setBus(DAC)` + `audio.tts()` |
| 4 | silent | 都没有 | 只打日志，不影响面板 |

两个坑已经写进注释，改这块时别删：

1. **起播前重建通路**：`play_stop` → `setup` → 音量 → `pm(RESUME)`。少了这段，
   第二句起 `play_start` 可能返回 true 却不出声；
2. **结束回调会丢**（被打断 / 被顶掉），所以每句都挂按字数估算的看门狗，回调带播报代次 `gen`，
   过期回调直接丢弃 —— 否则 `busy` 一旦焊死就永久静音。

音量、功放脚、冷却间隔都在 `theme.lua` 的 `M.audio`（`vol = 18`、`pa_ctrl = 73`）。
读法兜底在 `voice.norm()`：`C → 摄氏度`、`kWh → 千瓦时`（先长后短）、`- → 零下`，
免得把 `-18.4C` 念成"减十八点四西"。

## 接真实数据

`cold_data.lua` 只对外暴露字段，UI 层不参与计算。改数据源时：

1. 保留 `M.zones[i]` 的 `{name, target, tol, product, temp, door, status, defrost, duty}`；
2. 保留 `M.state.{hour, comp, avg}`、`M.today.{kwh, peak, doors, over, save}`、`M.events`；
3. 把 `M.tick()` 里的仿真推进换成"读 Modbus 寄存器 / 吃 MQTT 上报"，然后调 `M.settle()` 做状态分级；
4. `M.start_defrost()` / `M.toggle_door()` 改成下发写寄存器（现在只改本地状态）。

事件流是**边沿触发**的：`settle()` 里 `st == 2 and z.status ~= 2` 才记一条，
所以接真实数据后不会因为"温度一直在超温"而每秒刷一条。

## 已知限制

- 温区数固定 8（矩阵 2×4 摆满一格 336×316），要加温区先改 `theme.tile` 与 `cold_data.zones`；
- 24h 历史是 15 分钟一格（96 点），接真实数据后建议按 15 分钟落盘到 `fskv` 或用 PGFS 存 CSV；
- 语音在 PC 模拟器上无声（`exaudio` 缺省不编进模拟器），界面会标注，属预期行为。
