# wpl_family_album —— 一个由 AI 生成的电子相册

这是一个跑在 Air8607（Air1603）10 寸 RGB 屏上的家庭电子相册：开机密码锁屏 → 首页 → 读取 SD 卡真实目录 → 每页 4 张缩略图卡片 → 点开满屏看大图，支持左右滑动、轻触呼出控制条、3 秒自动轮播、亮度调节和 SD 空间查看。

**整个项目从零到可用，代码主要由 AI 生成**：人只负责提需求、把真机日志丢回来、验证效果；AI 负责架构设计、读 LuatOS 源码求证、写代码、按日志定位问题并迭代。下面记录这个「用 AI 生成项目」的过程和方法，作为一份可复用的说明。

---

## 一、AI 是怎么一步步把它做出来的

### 1. 需求拆解
先用自然语言把需求拆成可落地的功能点，再映射到技术模块：

| 需求 | AI 拆出的模块 |
| --- | --- |
| 开机锁屏 | `ui_lock.lua` + `lock.lua`（4 位数字键盘 + 密码持久化） |
| 首页 | `ui_home.lua`（渐变、卡片、时间、SD 状态） |
| 读 SD 卡 | `sd_card.lua`（SPI 挂载、目录枚举、JPEG 头解析） |
| 目录预览 | `ui_browser.lua` + `thumb.lua`（2×2 卡片 + 离线缩略图） |
| 满屏看图 | `ui_viewer.lua` + `photo_view.lua`（手势、轮播、控制条） |
| 页面跳转 | `app.lua`（状态机 + toast + 触摸分发） |

### 2. 技术选型：读源码，而不是凭经验
AI 没有按「相册就该用 image 控件」的直觉写，而是先读了 `LuatOS/components/airui` 和 `videoplayer` 的 C 源码，确认了每个组件真实的能力边界，再决定方案。这一步直接决定了后面少走弯路。

### 3. 编码
每个模块独立成文件、按「改板子只改 `conf.lua`」约定解耦；UI 统一走 `theme.lua` 封装的 label/button/card/shape，配色集中管理。

### 4. 真机日志驱动的迭代
这是最花时间、也最体现 AI 价值的一环：烧机 → 看日志 → AI 定位 → 改 → 再烧。整个项目是靠日志一次次「喂」出来的。

## 二、AI 靠「读源码」而不是「猜」解决的几个关键问题

这些问题的根因都不是从报错表面能看出来的，AI 是顺着源码一层层挖到的：

| 现象 | AI 读源码后的结论 |
| --- | --- |
| 反复 `hzjpeg alloc fail`（需要 1843200 连续内存） | `airui.image` 直接解 JPEG 是 RGB888 全尺寸（1024×600×3=1.84MB）且进 4MB 图片缓存，缓存按 LRU 在「新图解码之后」才淘汰，翻页峰值 3.7MB+，堆一碎就必崩。 |
| `airui.video` 换图建到第 2/3 个就 OOM | 每个 video 控件固定 2 块 RGB565 帧缓冲（2.46MB），且方法表里没有 `set_src`，只能 destroy+create，堆不合并碎片。 |
| 照片切换上屏 1240ms | 固件 `LV_BIN_DECODER_RAM_LOAD=0`，`.bin` 是**每次重绘都按行从 SPI SD 重新读 1.23MB**（600 次 seek+2KB 读），跟照片内容无关，所以每次恒 1240ms。 |
| 5 张照片只显示 4 张、下页置灰 | `ui_browser.build_page` 先画顶栏（用旧 `page_count=1`）后算页数，翻页按钮被锁死。 |
| 高分辨率手机照直接放进去显示失败 | videoplayer 的 sw 解码器（tjpgd）写死 `scale=0`（不缩放）、输出原图尺寸；且单帧 JPEG >2MB 被 `VP_MAX_FRAME_SIZE` 直接拒收。 |

最终方案也由 AI 定下：**「解一帧 RGB565 → 写 LVGL `.bin` → `airui.image` 按行读」**——运行期不占大块内存、不进图片缓存，只在首次看某张照片时申请一次内存。

---

## 三、AI 是怎么求证这些结论的（方法）

不是靠「我觉得」，而是靠工具一层层读：

1. **读组件 API 绑定**：确认 `airui.image` 的 `src` 只接受文件路径、`airui.video` 没有 `set_src`、`container` 没有 `set_size`、`slider` 的 `on_change` 只在拖动时触发——这些细节决定代码怎么写。
2. **读底层实现**：`lv_bin_decoder.c` 的 `decode_area` 里 `fs_read_file_at` 一行一次 seek+read；`airui_full_refresh` 内部是 `lv_refr_now()`（同步重绘，能用来拆开「取图」和「上屏」计时）；`luat_videoplayer_mjpg_sw.c` 里 `luat_jd_decomp(..., 0)` 写死不缩放。
3. **读平台配置**：`lv_conf.h` 里 `LV_BIN_DECODER_RAM_LOAD 0`；`fatfs.getfree` 返回的是 KB 单位；SD 卡走 SPI1 20MHz——直接解释 1240ms 的来源。
4. **查组件可用性**：`airui.slider` 是否注册、`fskv` 在整机固件上不可用（所以密码/亮度落到 SD 卡隐藏文件）。

一句话：**AI 把 LuatOS 当成一个可查询的代码库去读，而不是当成黑盒去猜**。

## 五、继续用 AI 开发这个项目的提示词示例

这个项目后续的改动，基本都能用类似下面的方式让 AI 接手：

```
需求：增加一个设置页，放在首页锁屏按钮边上，包含 SD 空间、亮度调节、修改密码。
约束：先读 <LuatOS 源码路径> 里的 airui/fatfs/pwm 相关源码确认 API 再动手；
      fskv 在整机不可用，持久化要落到 SD 卡隐藏文件；
      内存紧张，不要引入新的常驻大缓冲。
```

AI 会自己去读源码、确认 API、给方案、改代码，人只负责烧机验证。

---

## 六、给 AI 的有效提示词要点

1. **给路径，不给口头描述**：让它自己去读 `LuatOS/components/...` 的源码，比人转述 API 更准。
2. **带真机日志**：把串口日志整段贴给它，它能把报错和源码对应起来。
3. **说清约束**：内存大小、fskv 不可用、SPI SD 读速慢、编译选项不可改——这些环境事实要提前告诉 AI。
4. **让它先求证再动手**：明确「先读源码确认，再写代码」，避免它凭通用经验写出跑不通的代码。

## 七、当前状态与已知边界

- 照片只支持 baseline `jpg/jpeg`；高分辨率原图（>2MB 或 >屏幕尺寸）**暂不能自动适配**，
  需先把图缩到 1024×600 再放卡，或改固件（tjpgd 加缩放 + 提高帧上限）。
- 切图上屏约 1.2s，瓶颈是 SPI SD 按行读 1.23MB bin；根治需固件 `LV_BIN_DECODER_RAM_LOAD=1`。
- 硬件：Air8607 + 10 寸 RGB 1024×600 + GT911（I2C1）+ SPI1 TF 卡 + PWM3 背光。
