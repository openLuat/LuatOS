## Phase 4: RAM 热代码 (2026-10-10, 待刷机实测)

思路: 指令数已砍半但时间收益打折, 瓶颈转为 flash XIP 取指 → 把热点函数搬进常驻 RAM。

机制与预算实测 (ec718hm):
- 所有 RAM 代码经 fcelf 压缩进 flash, 受 zip 组预算约束: grp0(ASMB SRAM) 上限 24576, 已用 15448; grp1(PSRAM_P0) 上限 98304, 已用 96912 —— **grp1 余量仅 1392B**
- ASMB 还有 VMA 硬顶: 固定段 `.unload_cpaon` 在 0xa800, zidata 结束于 0x9d94 → 余量 2668B
- 16 个热点函数全搬需 +12444B zip (21.8KB 解压) → 超预算 11052B, 直接链接/打包失败

本轮 (探针版, 零配置改动, 预算内):
- G729_HOT (PSRAM_P0): Pred_lt_3, Cor_h_X, Syn_filt, Residu, Convolve (~1.2KB 解压)
- G729_HOT2 (ASMB SRAM): Corr_xy2, Weight_Az (~1.7KB 解压)
- 覆盖编码耗时 ~35% (Pred_lt_3 11.5% + Cor_h_X 9.4% + Syn_filt 9.8% + Corr_xy2/Residu 等)
- 结果: grp0 16504/24576, grp1 97700/98304 ✓; map 确认 VMA 落位正确; PC 回归 4/4 PASS (宏为空)
- ACELP_Code_A(8KB)/Pitch_ol_fast(5.2KB)/Qua_lsp/Autocorr 因预算未能搬入, 留在 flash

设备实测 (探针版 vs p123_O2):
| 配置 | 编码 avg µs/帧 | 编码 min/max | 编码实时 | 解码 avg µs/帧 | 解码实时 |
|---|---|---|---|---|---|
| p123_O2 | 5480.5 | 5294/6270 | 1.82x | 1164.5 | 8.59x |
| +RAM探针(7函数) | **5353.6** | 5210/5925 | **1.87x** | **1153.6** | **8.67x** |

探针收益: 编码 -2.3%, 解码 -0.9%。XIP 取指是真实但温和的瓶颈。
全量搬入 (再+19KB, 含大块头 ACELP/Pitch_ol, 缓存冲刷主力) 预估编码再 -3~8%。

### 全量搬入 (用户批准 bump grpSize 后)
- `PLAT/device/target/board/ec7xx_0h00/ap/gcc/sectionInfo_ec718hm.json` grp1: 98304 → 131072
- 16 个热点函数全部标注 (G729_HOT→PSRAM_P0 14个, G729_HOT2→ASMB 2个)
- 实测预算: grp0 16508/24576, grp1 **108384/131072** ✓; 压缩区物理余量 ~126KB 未动

- 固件: out/LuatOS-SoC_V2053_Air8000_122.soc (16:25) → 第6轮刷机待测

### 第6轮实测 (全量搬入)
| 配置 | 编码 avg µs/帧 | 编码 min/max | 编码实时 | 解码 avg µs/帧 | 解码实时 | 编+解 合计 |
|---|---|---|---|---|---|---|
| p123_O2 (无RAM) | 5480.5 | 5294/6270 | 1.82x | 1164.5 | 8.59x | 6645 |
| 探针 (7函数/2.9KB) | 5353.6 | 5210/5925 | 1.87x | 1153.6 | 8.67x | 6507 |
| 全量 (16函数/21.8KB) | **4736.4** | 4573/5538 | **2.11x** | 1199.5 | 8.34x | **5936** |

- 编码: 对 p123_O2 **-13.6%**, 对探针 -11.5% → 大块头(ACELP_Code_A 8KB / Pitch_ol_fast 5.2KB)
  确实是 fetch stall 主力, 搬进 RAM 后收益远超探针版外推
- 解码: 对 p123_O2 +3.0%, 对探针 +4.0% (退化; min/max 同时变差, 且探针→全量之间
  只有 Lsp_get_quant 与解码相关, 无法解释 4% → 疑为抖动或 PSRAM 代码体量效应, 待复测)
- 全双工单通道 CPU 占用: 6645µs → 5936µs / 10ms 帧 (66% → 59%)
- 代价: flash +11.5KB (压缩后 96912 → 108384)

复测 (同一固件重启重跑 3 次, 确认非抖动):
| 轮次 | 编码 avg | 解码 avg |
|---|---|---|
| 1 | 4740.3 | 1206.2 |
| 2 | 4736.1 | 1201.9 |
| 3 | 4732.8 | 1189.0 |

编码复现性极好 (±4µs); 解码稳定在 ~1199 (对 p123_O2 +3.0%) → 退化真实。

### 解码退化归因 (结论: 接受)
- 探针版(PSRAM 仅 +1.2KB)解码 1153.6 优于基线; 全量(PSRAM +21.8KB)解码 1199.5
- 探针→全量新增的 9 个函数里只有 Lsp_get_quant 与解码相关(丢包擦除路径), 解释不了 4%
- 解码侧共用的 Syn_filt(6处)/Residu/Pred_lt_3(2处)/Weight_Az(2处) 在探针版就已在 PSRAM
  → 退化不是"解码代码被搬走", 而是 **PSRAM 代码段体量效应** (该段与网络热路径
  soc_tcpip_rx_cache 共用, 共 25KB; 疑 PSRAM 取指缓存容量被挤)
- 该退化无法通过"少搬"消除: PSRAM 体量由要保留的大函数主导, 且探针版已证明小函数搬入对解码无害
- 量化: 46µs/帧 = 单帧的 0.8%; 解码仍 8.3x 实时, 非瓶颈。**接受当前配置**

### Phase 4 最终结论
编码 5480.5 → **4736.4 µs/帧 (-13.6%, 1.82x→2.11x)**, 解码 1164.5 → ~1199 (+3.0%, 8.34x)
单通道全双工: 6645 → 5936 µs/10ms 帧 (-10.7%)
遗留风险提示: g729 占用 PSRAM 常驻代码段后, 与网络/IMS 热路径争用该段取指缓存。
若后续集成测试发现网络收发延迟变差, 首选回退方案是只保留 ACELP_Code_A + Pitch_ol_fast
两个大块头在 PSRAM (约 13KB), 其余回 flash。

若实测收益明显, 下一步: bump sectionInfo_ec718hm.json grp1 (98304→131072)。
依据: 压缩区总空间 filesize-flashXIPLimit=251024B, 当前两组只用 ~125KB, 余量 126KB;
boot_code.c 从镜像头动态读段表解压, grpSize 仅为打包预留值。失败模式为打包报错或
启动失败(可重刷恢复), 需用户确认后实施。

## Phase 5: 原语层重写 + LSP 量化精确剪枝 (2026-10-10)

三件事一起落地: `basic_op.h` 原语重写、`qua_lsp.c` 部分距离提前退出、阶段 cycle profiler。

### 设备实测 (Air8000/ec718hm, 128帧 tame.pcm)
| 配置 | 编码 avg µs/帧 | 编码 min | 编码实时 | 解码 avg | 解码 min | bit-exact |
|---|---|---|---|---|---|---|
| Phase 4 定稿 | 4736.4 | 4567 | 2.11x | 1168.4 | 1123 | PASS |
| Phase 5 (本轮) | **4300.5** | **4135** | **2.33x** | 1183.3 | 1134 | PASS |

编码 **-9.2%** (min -9.5%), 解码不变 (1134 vs 1123 属噪声)。对 -Os 基线累计编码
**-42.4%** (7460.5 → 4300.5)。单通道全双工核算: 4300+1183 = 5.48ms/10ms 帧。

### 1. `basic_op.h` 原语重写 (bit-exact)
- `L_shl`/`L_shr`: 去掉倍增循环, 用 `u >= 2**(31-n)` 单次比较判饱和
  (实测 1196 次/帧, 平均只需 2.63 次倍增, 原实现却每次都走循环)
- `L_mac`/`L_msu`: 展开融合, 去掉中间层重复的溢出判断 (25234 / 4813 次/帧)
- `L_add`/`L_sub`: 饱和限值改从**回绕后的结果**取符号 → 少一个跨溢出判断的活跃变量
- 整库 `.text` 反而变小: 63066 → 61890

验证: 主机差分比对 8612 万次 (原型) + 3466 万次 (真实头文件), 0 不一致;
真实头文件路径与 ACLE 路径均已覆盖。

### 2. `qua_lsp.c` LSP 量化精确剪枝 (bit-exact)
- `Lsp_pre_select` / `Lsp_select_1` / `Lsp_select_2` 加部分距离提前退出
- 依据: 每一步累加项恒非负 (平方项 / 权重×平方, 权重已核实恒非负), 故运行中的距离
  单调不减、是最终距离的下界; 达到 `dmin` 即可放弃该候选, 不改变胜者
- 主机等价性测试: **真实的剪枝后代码** vs 未剪枝参照, 900 万次调用 / 7.68 亿候选,
  **0 不一致** (含全 -32768 饱和边界、码本向量、退化向量)
- 剪枝效率: 平均计算维度 **10 → 5.598** (真实编码器输入下 96.2% 候选被提前淘汰);
  `select_1` 3.768/5, `select_2` 3.979/5
- 灵敏度反证: 故意喂负权重 (真实输入不可达) 时 20 万次有 14.99 万次不一致 → 比对非恒真

### 3. 阶段 cycle profiler
- `g729a_profile.{c,h}`: 13+2 个阶段, DWT->CYCCNT (M3) / rdtsc (PC)
- `G729A_PROFILE` **编译期**开关, 默认 0 = 完全编译掉; 已验证默认构建的 `cod_ld8a.o`
  与未插桩版本**指令流逐条完全一致** (763 条)
- 暴露为 `codec.g729prof()`; 新测试套件 `testcase/func/g729/g729_profile_basic`

### 失败记录 (教训)
第一版 profiler 用"运行时开关 + 每阶段调一次外部函数", 目标实测编码**慢了 1.4%**
(min 4568 → 4637): 那个外部调用被 GCC 当作 memory clobber, 破坏了 `cod_ld8a.c`
子帧循环的优化 —— 该文件 `.text` 2340 → 3352 (+43%)。改成编译期开关后消失。
**教训: 插桩必须能被完全编译掉, 不能靠运行时分支。**
第二条教训: 不要在同一个固件里同时改两件事 (本轮一度无法区分是原语重写还是插桩导致的
退化), 否则刷机轮次会被白白浪费。

### Phase 5 目标阶段分解 (DWT CYCCNT, 128 帧)
| 阶段 | 占比 | 计数/帧 |
|---|---|---|
| enc.sf.pitch (`Pitch_fr3_fast`+`Enc_lag3`) | **36.4%** | 256 |
| enc.lspq.qua (`Qua_lsp`) | **~26%** | 128 |
| enc.lpc (Autocorr+Levinson+Az_lsp) | 9.2% | 128 |
| enc.sf.fixed (`ACELP_Code_A`) | 8.1% | 256 |
| enc.wsp | 6.4% | 128 |
| enc.sf.gain | 5.3% | 256 |
| enc.sf.filter | 4.3% | 512 |
| enc.vad / enc.pre / enc.lspq.waz / enc.misc | 2.2 / 0.5 / 0.8(PC) / 0.2% | |

- 插桩位置已核对: `sf.pitch` 确实只包 `Pitch_fr3_fast` + `Enc_lag3`, 无多包
- `enc.lspq.waz` (`Int_qlpc` + 2×`Weight_Az`) 仅 0.8% → 原 `enc.lspq` 的 27.5% 几乎
  全在 `Qua_lsp` 内部; 而三个搜索循环只占全帧 25234 次 `L_mac` 中的约 3200 次,
  剩余大头在预测器/多项式转换 (`Lsp_prev_extract` / `Lsp_prev_compose`+Chebyshev /
  `Lsp_get_quant` / `Lsp_lsf2`+`Lsf_lsp2`)
- 与论文对照 (论文: 自适应码书 16.3%, 固定码书 21.5%, Qua_lsp 17.6%, LPC 分析 15.8%):
  **两边排序几乎相反** —— 我们的闭环基音搜索是论文的 2.2 倍占比, `ACELP_Code_A` 只有
  论文的 1/2.7。论文的优先级 (先啃 ACELP) **不能照搬**
- 阶段之和 = 1,393,477 ticks/帧, 除以实测 4800 µs/帧 → **核心频率 ≥290 MHz**
  (本文档标题的 204MHz 偏低, 待修)。阶段之和 ≈ 整帧耗时 → 分解无漏算

### 未采纳: 论文的"去除饱和运算"
实测 128 帧里各饱和分支的真实触发次数: `L_sub` **720 次** (5.6 次/帧)、`L_add` 51 次、
`L_mult` 2 次。去掉检查会直接改变输出, 且累加器回绕可能产生可听杂音 → **不采用**。
(论文以"预处理已定标"为据去除饱和, 在我们的代码上不成立。)

### Phase 5 细化插桩: 两个大阶段的内部构成 (PC, 三轮, 子项之和与旧父括号一致)

把 `Pitch_fr3_fast` 与 `Qua_lsp` 从"一个括号"拆成互不重叠的子分档 (共 24 档), 因为
主机侧"按函数归因指令数"在这份代码上**不可靠**: 内联打乱归因, 会报出
`g729_Pitch_ol_fast` 的指令数比整个 `sf.pitch` 阶段还高, 与目标实测占比矛盾。

| 子阶段 | PC 占比 | 组内 | 说明 |
|---|---|---|---|
| `enc.pitch.frac` | **11.3%** | 64% | `Pred_lt_3`×3 + 点积×3 + Copy + 分数判决 |
| `enc.lspq.presel` | **6.0%** | 52% | `Lsp_pre_select` (已剪枝) |
| `enc.pitch.corhx` | **5.0%** | 29% | `Cor_h_X` (40×40 相关) |
| `enc.lspq.sel12` | 3.2% | 28% | `Lsp_select_1/2` (已剪枝) |
| `enc.pitch.int` | 1.4% | 8% | 整数 lag 相关循环 |
| `enc.lspq.pred` | 1.0% | — | prev_extract + buf 拷贝 + expand + get_tdist |
| `enc.lspq.waz` | 0.8% | — | `Int_qlpc` + 2×`Weight_Az` (含 `Get_lsp_pol`) |
| `enc.lspq.quant` / `conv` / `wgt` | 0.5 / 0.4 / 0.3% | — | 重建 / LSP↔LSF / `Get_wegt` |
| `enc.sf.pitch` | 0.1% | — | 现在只包 `Enc_lag3` |

分区完整性 (三轮): Pitch 子项和 17.6/17.3/17.1% vs 旧 `enc.sf.pitch` 16.2~17.5%;
Qua_lsp 子项和 11.5/11.4/11.5% vs 旧 `enc.lspq.qua` 11.2~12.6%。调用次数断言逐项通过。

**修正了一个此前的错误假设**: `Get_lsp_pol` 与 Chebyshev (`Chebps_10/11`) **不在**
LSP 量化器里 —— `Get_lsp_pol` 经 `Lsp_Az` 从 `Int_qlpc` 进入 (属 `enc.lspq.waz`),
`Chebps_10/11` 只经 `Az_lsp` 进入 (属 `enc.lpc`)。所以 LSP 量化器 80% 的代价就在
两个 VQ 搜索里, 而这两个搜索已经剪枝过了。

### bit-exact 路线已基本榨干 (逐项验证过的死路)

| 项 | 结论 |
|---|---|
| `Pred_lt_3(frac=0)` 当拷贝 | **不成立**。frac=0 等效于以 `exc[n]` 为中心的对称 19 抽头 FIR (`a[0]=29443` + `±1..±9` 对称项, 直流增益 32723 ≈ 2^15), 三条分数都是真实插值 |
| 整数 lag 循环用部分距离剪枝 | **不成立**。它找的是相关**最大值**, 部分和可为负, 不是下界 |
| `Cor_h_X` / `Dot_Product` | 内生的 40×40 相关与 40 点积, 无可削减结构 |
| LSP 搜索再剪枝 | 平均维度已到 5.598/10, 接近该结构的下限 (剩余项恒非负是下界唯一来源) |
| 论文的"去除饱和" | 本平台实测 `L_sub` 5.6 次/帧真的会饱和 → 不安全 |

### 下一步: 有损路线 (需要质量门控)
bit-exact 能拿的已拿完。剩余代价集中在 **内生的乘加/取表工作量**, 要再快必须减少运算
次数, 也就是改变输出。按实测占比排序:

1. `enc.pitch.frac` (PC 11.3%, 组内 64%) —— 三条分数插值只算 2 条, 或第二子帧跳过
   分数细化。最大单块, 估约 -8% 编码时间
2. `enc.sf.fixed` (目标 8.1%) —— 收紧 ACELP focus search 阈值
3. `enc.lspq.presel` (PC 6.0%) —— 更粗的预选 / 级联剪枝

前提: 先把**质量评估台**建起来 (以 `tame.pcm`/`tame_ref.pst` 为基准的分段 SNR 等客观
失真指标), 并配合 SIP 链路实听, 才能判断哪个取舍可接受。改代码前先有尺子。

### 质量评估台 (已建: `testcase/func/g729/g729_quality_basic`)

纯 Lua, PC 可跑。三个用例:
1. `test_bitstream_diff` — 码流逐字节/逐比特/逐帧比对, 给出首个不同的帧号
2. `test_pcm_quality` — 解码后算 全局SNR / 分段SNR (80 采样一帧, 逐帧裁剪到 [0,35]dB 再取均值)
   / RMS 电平比; 同时对"新解码 vs 源语音"和"参考解码 vs 源语音"各算一遍
3. `test_metric_sensitivity` — **故意损坏 1 帧码流**, 证明度量有分辨率, 否则"通过"没有意义

**关键发现: 不能用"新码流 vs 参考码流"的 segSNR 当 lossy 门槛。**
G.729 解码器是闭环自适应的 (`gain_pit` 可达 1.2, 无绝对刷新), 误差被无限回收而不衰减:
损坏第 64 帧后, 后面 64/128 个分段全部低于 20dB, 到文件结尾也只回到 9.1dB。
所以单帧全字节取反就能把该指标从 35dB 打到 19.86dB —— 它度量的是**发散度**, 不是质量,
用它做门槛等于"不许有任何一帧的判决改变"。

正确门槛挂在**源参照**指标上: `segsnr(新解码, tame.pcm) >= segsnr(参考解码, tame.pcm) - 0.5dB`。

参考基线 (PC 实测, 128 帧 tame):
| 度量 | 值 |
|---|---|
| 参考解码 vs 源语音 | segSNR 18.46dB, 全局SNR 15.65dB, RMS -0.66dB |
| 参考解码 vs 源语音 (p5) | 15.85dB |
| 干净码流自比 | 35.00dB (裁剪上限, 即完全一致) |
| 单帧损坏后 (发散度) | 19.86dB, min 0.00dB, p5 0.17dB |

即 8kbps G.729A 在这个序列上的固有代价是 18.46dB segSNR; lossy 改动必须让新解码
相对源语音保持在这个水平附近, 而不是要求它与参考码流一致。
